### 生产实例实测

- 重启后新 PID <已隐去>，旧进程终止；`GET /antenna-optimizer` → 200 / 187400 字节，SHA256 与 `plugin/panel.html` 一致
- `POST` → 405 且 `Allow: GET, HEAD`（**这是区分新旧代码的唯一判据**，1.0.0 不可能有此输出）
- **canary 测试**：在生产行的 `config` 里写入 `routePath: /antenna-optimizer-canary`，
  热加载后 `/antenna-optimizer-canary` → 200、`/antenna-optimizer` → 404；
  还原后逐字节复原，原路径恢复 200。**新配置能力在生产上端到端生效。**
- 回归：`test/test-acceptance.cjs` 对插件路由 `passed: true`，零失败

### 两个实施中发现的硬事实

**1. 改代码必须重启，改配置不需要。** 二者机制不同，已实测：

- 用 patch 热重载把条目卸载再挂载，运行中的进程仍执行**旧代码**——loader 重新 import 的是同一模块 URL，Node 的模块缓存不失效
- 但改 `config` 能热加载生效，因为模块已带着 `Config` 导出加载，只是重新解析配置

**2. 本机合成树里没有 logger 条目。** 因此未知键告警不能只依赖 `ctx.get('logger')`，否则方案 B 的残留风险（拼错键名静默无效）会重新变成不可见。实现改为 logger 优先、`console.warn` 兜底，且只在挂载时告警一次——即教程第 3 章「可选依赖：跳过 inject，在使用处探测」的写法。

### 原「必须权衡的副作用」如何被方案 B 处理

严格拒绝未知键时，**配置里一个拼写错误会让整个 `dsh web` 启动失败**（实测 `plugin tree failed to load`），而不只是这条路由失效。方案 B 把未知键降级为**告警而非失败**：

- 类型/格式错误仍然拒绝启动（这才是真正会导致"配置写了却毫无效果"的那类问题）
- 拼错键名不再阻断启动，但**不静默**——挂载时输出一行告警

爆炸半径从「整个 harness 起不来」收敛到「一行告警 + 默认值生效」。

### 一项必须权衡的副作用

采用严格 schema 校验后，**配置里一个拼写错误会导致整个 `dsh web` 启动失败**，而不只是这一条路由失效。实测输出：

```
Error: dsh: plugin tree failed to load: failed to apply loader entry
antenna-optimizer-panel (dsh-em-agent): invalid config: …
```

这是教程第 5 章要求的行为（「错误配置会导致加载失败」），但影响面是整个插件树。若认为这个爆炸半径过大，可折中为**只校验类型、不拒绝未知键**（去掉附录 A 中的 unknown-key 检查），仍能捕获 3.1 实测的那类「配置被静默忽略」问题而不会因拼错键名直接拒绝启动。这是一个取舍，不是纯技术优劣。
